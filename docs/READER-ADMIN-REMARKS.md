# 作者私有用户备注

作者可在新版后台为已验证读者保存、修改或清空一条备注。备注不是昵称，不参加社区展示、身份桥接或读者资料审核。正文只在作者鉴权的用户管理列表和对应操作回执中返回。

## 存储与权限

备注存于主站 `content.db` 的 `readers.admin_remark` 可空文本列。Payload 字段隐藏，通用字段 create/update/read 访问全部拒绝；作者管理服务完成现有身份和来源检查后，才显式读取隐藏字段并输出自己的 `remark` 投影。普通读者登录、session、作者个人身份、社区身份及公开资料继续使用原有白名单 DTO。

`POST /api/manage/readers/:id/remark` 只接受 `{confirmId, remark}`。编号必须匹配，备注必须是字符串，去除两端空白后最多 200 个 Unicode 码点；空字符串将列清为 NULL。写操作复用既有账号操作串行队列，执行时重新检查作者权限及账号存在性。审计只记录动作、是否清空和长度，不记录备注正文、旧值或搜索词。

用户列表的 q 搜索复用原来源和权限边界；有搜索条件时在 SQLite 使用参数绑定的 `instr/lower` 查询昵称、邮箱、手机号、备注及 UID 对应账号，只取得当前页最多 20 个 ID 和总数，再由 Payload 完成资料投影。`%` 和 `_` 按普通字符匹配，不当作通配符。账号状态、VIP 状态和排序仍沿用原规则。搜索词最多 80 个 Unicode 码点。

## 本地与未来部署

本地独立合成预览使用 `push:true` 新建完整表，不读生产配置。真实数据启动保持 `push:false`；新版本只检查该列已准备，不在启动时自动迁移。

未来若授权发布，先按 `docs/MAINTENANCE.md` 备份、校验异地副本，再对准确的主站私有数据目录执行既有命令：

```sh
node scripts/migrate-reader-accounts.mjs <private-payload-directory>
```

该工具先创建 schema 备份，再在事务中补缺失列；已有备注不覆盖，重复运行不产生修改。不需要迁移香港社区数据库或向身份桥增加字段。旧程序在 schema push 关闭时可继续使用新增列后的数据库；回滚代码不得回滚用户新写入的数据。

主站原 `backup-payload.mjs` 通过 SQLite backup API 备份整份 `content.db`，自然包含私有备注。人工删除和闲置自动清理都删除账号整行，备注同时移除，没有另一个备注侧库。清空或删除不会抹除历史维护备份，历史备份仍按既定权限与保留期限管理。

前端需避免把备注搜索词存入可分享 URL 或 localStorage；新后台仅在内存保存筛选。正式发布审查还应核对反向代理与访问日志对 `/api/manage/readers` 的 query 处理，避免把私有搜索词写入长期访问日志；本次本地迭代没有修改线上日志配置。

### 正式运行模式与代码回退演练

`tests/reader-admin-remarks-release.test.ts` 为显式开启的本地交付演练。它需要 Node 24.21+、已按锁文件安装的依赖、Git、tar，以及本地 Git 中的历史提交 `3d213699172f00ba054bb9d118635ed99f4493c6`（私有备注功能前的已提交源码）。缺少历史提交时不能把演练记为通过，也不以猜测旧代码替代。普通测试默认跳过，交付检查必须显式开启：

```powershell
$env:ADMIN_REMARKS_RELEASE_DRILL = '1'
node --test tests/reader-admin-remarks-release.test.ts
```

演练先在本次新建的 `.local/reader-remarks-release-drill-*` 下生成合成作者、读者、UID、VIP、文章、头像和小附件。只有建造合成旧库的准备阶段使用测试环境 schema push；后续新旧版本启动均使用 `NODE_ENV=production`、显式 `push:false` 配置和实际 `createPayloadRuntime`。每一阶段是独立子进程，完全关闭后才执行下一阶段，防止 Windows 的原生数据库句柄干扰代码切换。它不会读取现有私有配置、线上数据库或真实账号；所需配置和随机密钥全部在本次目录内生成。

验证顺序：

1. 移除合成库的备注列，新版本正式运行模式必须拒绝启动；核对数据库字节未发生变化。
2. 调用现有 `backup-payload.mjs`，检查清单中各文件哈希和 SQLite 完整性，再用 `restore-payload.mjs` 恢复到另一个新目录核对，不能覆盖演练中的数据目录。
3. 显式执行 `migrate-reader-accounts.mjs`；检查迁移前快照、原账号/UID/VIP/文章/设置/上传不变，新增列存在，重复迁移不再修改。
4. 启动新版本的完整主站运行时，通过真实本机 HTTP 完成作者和读者登录、备注保存、VIP 修改，另外新增一位合成读者。再次备份，验证备份包含新备注与新增账号。
5. 从上述 Git 提交将 `server`、`src`、`server.mjs`、`package.json` 提取到全新代码目录，启动该历史源码；仍使用同一个迁移后的数据目录和已经安装的安全依赖。原账号与新账号均可登录，UID 保持，旧后台仍能修改 VIP；旧 DTO 不会突然显示它尚不支持的备注。
6. 切回当前代码，确认新备注、新增账号及回退期间的合法 VIP 修改仍存在；比较文章、个人设置、密码哈希、UID、头像和附件，检查 schema 未被旧版本删减。结束后只清理本次生成且已核对路径的演练目录。

该演练验证的是**新增备注列与既有业务的兼容性，以及只回退代码、不回滚数据**。它不授权使用任意旧版本上线，不覆盖实际服务器文件权限、反向代理配置或数据库现状；正式回退版本仍须保留已修复的安全补丁。依赖继续使用当前锁定的 Payload 3.90.2，不回退到 3.89。演练为隔离数据而显式关闭登录滑块，正式登录验证链由单独的后台登录交付用例负责，不能用本演练替代。
