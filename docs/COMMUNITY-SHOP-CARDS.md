# 道具卡上架与用途纠错

2026-10-09：作者可在原有兑换所上架流程中创建补签卡，并纠正尚未被兑换的错误物品类型。商品分组和物品用途是两个字段：分组由作者自建，不决定兑换后发放什么权益。

## 物品与接口

沿用 `POST /api/community/manage/items` 和 `POST /api/community/manage/items/<id>`。新建与完整编辑补签卡使用 `cat: "card"`、`kind: "card"`、`ref: "makeup"`，其余价格、图片、库存、限兑与最低等级条件沿用既有商品规则。图片仍须是本人上传且用途为 `shop` 的有效图片。物品用途在服务端检查白名单，不从名称、说明或兑换后的交付文字推断。

数据库明确存储 `community_shop_items.cat="card"`、`kind="makeup"`。已有道具实现的 `pin`、`highlight` 也列在受控枚举中，不能写入任意道具名。现有装扮保留原有 `cat="digital"` 与 `kind="frame"/"color"/"cover"` 的存储和 DTO 映射，不改写历史物品。

兑换补签卡在原事务里扣除星尘、扣除有限库存、创建已完成订单并增加 `community_inventory.makeup` 一张；不创建数字资源拥有记录，不要求收货信息。原有幂等请求标识、限兑、权限与余额检查继续生效。

仅上下架时，向原有带 ID 保存地址提交精确的 `{ "active": false }` 或 `{ "active": true }`。该操作只更新上架状态和更新时间，不能把客户端缓存的整行旧价格、库存或交付内容回存。真实商品仍保留，历史订单及权益不受上下架影响。

## 纠正误上架类型

没有任何兑换订单、拥有记录或既有佩戴引用时，作者可修改物品用途，保留原 ID、图片、分组和创建时间，清理新用途不适用的交付内容或昵称特效。

只要存在该物品的历史订单，包括已取消订单，或拥有记录、既有佩戴引用，就不能改变用途或卡种。商品仍可修改文案、价格和上下架状态；已被兑换的头像框或主页背景继续沿用原有使用图片保护。误上架且已有兑换的物品，应下架并另建正确用途物品，不删除旧订单、不自动补发卡、不将数字资源拥有记录改造成卡。

管理接口给出 `canChangeKind` 供编辑器说明状态。最终判断仍在同一个 `BEGIN IMMEDIATE` 事务中完成，不能凭客户端标志放行；与兑换并发时，按先提交的合法业务结果保护权益。

## 补签卡说明

每张补签过去七天内漏掉的一天，不含当天。普通读者每个北京时间自然月最多补签两次，有效 VIP 最多三次，持卡不增加次数。次数按执行补签的月份归属，月初补上月日期仍占本月次数。

使用时优先消耗已有补签卡。无卡且有效 VIP 当月尚未补签过时免费，否则消耗三十星尘；持卡完成首次补签后，不另保留一次免费补签机会。补签接续连签、参与徽章核算并计入被补日期所属月份的满勤，不补发当日普通或 VIP 签到星尘。凑齐自然月可触发该月一次的满勤五星尘。卡没有过期时间字段；七天限制指可补日期，不能写为卡七天后过期。

## 迁移与发布

本次属于显式 schema 更新，不能套用零迁移发布。启用社区的宿主须先完成持久数据、上传文件和配置备份并验证异地副本，再按现有维护流程运行 `node scripts/migrate-community.mjs <private-data-directory>`。主站与社区宿主按真实配置分别判断，不向未启用社区的主站盲目创建社区表。

迁移先创建 `schema-backups/` 快照，再在事务中重建 `community_shop_items`，只扩大已知枚举并加入 `community_shop_card_kind_check` 合法组合约束。保留所有原列、行、ID、原值、索引和触发器，外键引用在提交前复核。不会自动纠正任何已有数字资源或改动其他业务表；重复迁移返回 `changed: false`。未知枚举无法安全识别时拒绝迁移，保留源表和备份。

发布前验证旧当前表、早期无装备列表、旧装备表的升级、完整性、外键、备份与幂等；验证新卡兑换、旧权益保护、失败回滚、重复请求和跨连接并发。

旧应用不认识正式 `card` 商品。新增卡行或用途纠错尚未发生时，才可能将应用指针回退到旧版并保留扩展 schema；一旦作者发布正式卡或纠正用途，不直接切回旧解释逻辑。采取保留在线最新数据的兼容前向修复；不把迁移前快照覆盖在线数据，不回删卡或订单以制造回滚条件。
