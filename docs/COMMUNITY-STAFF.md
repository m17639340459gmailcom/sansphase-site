# 社区管理职务与权限维护

正式源码中的管理职务与自动信任等级分开。站长、总版主、版主、协管来自服务端任命；初光、巡天、观测、守夜仍由既有访问、阅读和贡献规则计算。任命不会增加经验、VIP、星尘或普通发帖额度。管理图标由合作作者提供，前端仅保留对应位置。

## 任命与授权

职务层级是站长 → 总版主 → 版主 → 协管。使用现有 `POST /api/community/members/:uid/steward`，不另建任命接口或申请表。申请使用管理联系方式，再由上级在管理台任命。

现代新增和配置请求明确提交 `on`、`role`、`boards`、`permissions`、`delegable`。撤销提交 `on:false`。`permissions` 是当前人员可执行的能力，`delegable` 是可再授予下一级的能力；任命能力本身与可委派能力分开。固定站长可直接任命总版主、版主、协管；总版主和版主仍只能任命相邻下一级。该例外只涉及管理职务，不授予新的固定站长账号、品牌作者登录、VIP 或成长等级。服务端任命写入和授权链读取使用同一职务规则，并继续核实当前有效板块和可委派能力的子集，不信客户端角色、按钮状态或声明的权限。协管即使被送入 `staff.appoint` 字符串也不能继续任命。

禁止任命自己、同级和上级，禁止修改别人的下级（固定站长可调整所有低级管理职务）。站长接管非直属成员时，其直属上级改为站长。撤销和角色/直属上级变化会同时撤销现有子树，并保留历史数据。界面在这类配置保存前显示警示，并对同一份配置要求再次确认；同角色、同任命来源的调整不触发子树撤销。以后重新任命某个账号不会恢复此前已撤销的下级。权限或板块缩减通过祖先交集即时限制下级；循环、孤立、损坏的授权数据失败关闭。

权限表按内容审核、内容维护、精选与横幅、资料审核、成员纪律、任命管理分组，每项权限只列一次，分别勾选可执行与可下发。只展示当前上级允许下发的能力。勾选下发会同时勾选执行，取消执行会清除下发；身份切换保留用户已配置的板块和权限，协管不能继续任命的限制在任命管理组说明。身份、范围或能力配置有未保存修改时，沿用原离开确认；保存中禁用字段、失败后保留选择。窄区域将权限名称和勾选列分行，不新增页面整体滚动层或覆盖式聚焦边框。

协管默认可以查所属板块内容、通过/驳回待审主题、提出精选推荐、提出资料审核建议。当前回复模型只有举报隐藏后的恢复/删除，没有“待审回复”或回复审批接口。删除已发布主题、删除回复、扣分、禁言和解除禁言分别授权；删除不会隐含额外违规扣分或禁言。正常删除仍沿用既有贡献冲正，避免已删除贡献继续领取奖励。

## 资料与精选

头像、个签、昵称、主页背景分别有 `advise` 与 `decide` 两项能力。资料属于全账号，没有板块归属；管理台必须明确显示全账号范围。查阅仅从该种类的建议/决定能力派生，不存在独立无限制的隐私查阅开关。建议不能替代最终审批，驳回须提供理由。主站审核通过原有签名桥即时回查真实角色、种类与动作，并核实当前账号和全部读者祖先的已验证/未停用状态。客户端的角色声明不是授权。

精选推荐使用 `POST /api/community/topics/:id/feature-recommend`，推荐不会触发星尘或精选奖励。管理台 `features` 页显示持久待办；有审批能力的对应版主或上级通过 `POST /api/community/manage/feature-recommendations/:id/approve` 或 `/reject` 决定。驳回须理由；通过沿用既有精选事务、奖励和通知，重复请求不会再发奖励。推荐人撤职、祖先授权变化或账号失效时不能审批其旧推荐。没有新增站长终审步骤。

## 每次使用都检查

每个请求建立自己的授权上下文。请求体、人物资料、文件编码/读盘、资料桥和实际写入前重新核实权限及活跃账号。相关业务参与者（任命目标、精选推荐人及其祖先）也加入该请求后续的活跃检查；不跨请求缓存授权。普通用户人物投影保留原姓名等公开字段，私有 `active` 仅用于后端鉴权，不下发公开人物 DTO。

管理台返回每个内容对象的可操作标记，隐藏按钮只是展示；服务端最终仍核实权限。举报处理需要所属板块举报权限，支持举报不能隐含删除权限，恢复隐藏内容不能隐含恢复权限，扣分仍另查扣分权限。移动帖子要求源、目标两边的授权。原守夜普通读者的标签编辑权限继续保留。店铺、订单、社区公约、徽章复核和首页横幅保持站长专属。

站长品牌身份仍使用固定站长账号。其个人读者身份没有管理能力；个人资料与品牌资料独立，读者身份可保留切回站长的入口，不能借此调用管理动作。

管理权限提供的强举报仅能作用于本人以外、职务低于自己的对象；对同级和上级仍按实际获得的普通信任等级处理举报，不能借举报越过管理处罚边界。汇总的会员板块计数、最新标题、标签和管理队列在异步人物/资料读取后重新检查可见范围。

主站资料审核先获取香港当前授权，核实主站账号，再复查香港授权与主站账号，并在返回前核实会话。两台服务器分别持有账号和任命数据，没有跨服务器原子事务；检查期间发现不一致或失效会拒绝操作，不缓存成功证明。

## 迁移、备份与回滚

上线前显式执行香港社区迁移和主站资料工作流迁移，并先备份及验证异地副本。社区新增 `community_staff`、`community_feature_recommendations`、`community_profile_background_advice`；已有背景审核表的 `by_kind` CHECK 从仅站长扩大到站长/读者。迁移保留既有账号、内容、订单、账本、上传登记、旧审核行以及原索引和触发器；源 `steward` 行不删除。

只有合法有效的旧 `steward` 数据迁为版主，保留原板块和既有能力，不自动成为总版主，也不获得新任命、精选终审或其他资料最终审批能力。损坏旧范围保留原行但不授予管理权限。固定站长可维护这些旧版主；省略现代角色/权限字段仅兼容固定站长调整现有旧版主，新目标必须使用明确的新协议。

原始未配置过的旧职务保留旧 `steward=1` 投影；现代新增或发生配置修改的职务把旧投影清零，权限由新表确定，避免旧程序把细分角色当作万能版主。旧程序回滚因此不能正常管理新职务，也不能被当作完整业务回滚方案。

站长直任三种管理身份的调整沿用该表，不需要额外迁移或改写原任命数据。回滚到仍只识别相邻层级的旧运行时，会使新建立的直属版主、直属协管权限链失效；旧代码会拒绝这些链而非扩展权限，不能以回滚数据库恢复业务。

出现新资料工作流或权限错误时先进入维护状态，停双方相关服务入口，再修复并验证。不得恢复旧资料写接口来绕过新审核，不得直接恢复旧数据库覆盖上线后的审核、建议、任命或账本。部署回执、实际目录和私有审计记录留在 `.ops`，不写入正式维护文档或公开 Git。
