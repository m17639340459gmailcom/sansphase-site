# 源码与服务器维护

本规则自 2026-09-27 起实施。网站业务运行版本无需为日常容量整理而切换。

## 源码入口与版本

项目根目录是唯一维护入口。历史 `.local/current-source-vip-days` 不再接收改动；根目录旧文件已在私有维护归档中保存，根目录独有的九个旧开发工具先保存在 `archive/maintenance-20260927/root-only/`。其中 `scripts/preview.ps1` 经核对仍由桌面预览入口使用，已保留回正式工具清单；其余八个历史工具不参与构建。

每次变更提交可审查的 Git 差异；仅添加明确源码清单，不执行 `git add .`。先检查凭据和真实用户资料，再提交。发布标签和维护标签分开；维护标签不代表已将新应用上线。

`src/` 负责前端；`server/reader-*` 负责读者认证、账号、VIP、审核与生命周期；`server/author-service.ts` 负责作者内容操作；`server/community-*` 负责社区业务与独立主机；`server/payload/` 负责主站存储；`deploy/` 是系统部署和运维工具。主站后台与主站运行在同一应用内；香港社区使用独立进程与数据库，通过身份桥接复用主站账号，见 [香港社区部署边界](COMMUNITY-HOSTING.md)。

## 必须保护的数据

生产持久数据以私有配置为准：主站当前位于 `/var/lib/sansphase/payload`，香港社区位于 `/var/lib/sansphase-community/data`。数据库、VIP 期限、读者头像、审核中头像、作者上传、配置、注册工作流均不属于旧发布清理范围。图片及音频缓存维持现状。不得因为早期文档只列主站目录，就遗漏香港备份或移动在线数据。

| 用途 | 主站 | 香港社区 |
| --- | --- | --- |
| 当前代码链接、版本 | `/opt/sansphase/current`、`/opt/sansphase/releases` | `/opt/sansphase-community/current`、`/opt/sansphase-community/releases` |
| 私有配置 | `/etc/sansphase/payload.json` | `/etc/sansphase-community/community.json` |
| 正式备份 | `/var/backups/sansphase` | `/var/backups/sansphase-community` |
| 维护工具、回执 | `/opt/sansphase-maintenance`、`/var/log/sansphase-maintenance` | `/opt/sansphase-maintenance`、`/var/log/sansphase-maintenance` |

隔离恢复与测试产物使用单独的维护工作目录，不再新增到正式备份根目录或当前 release。已核对的构建测试产物归档到私有 `/var/lib/sansphase-maintenance/artifacts/<host-release>`；先核对异地恢复副本、文件哈希与运行引用，再处理精确清单，不移动浏览器使用的 dist。已有用途不明的副本先核对、留存恢复证明，再按清单处理；目录名字不是删除凭证。

整理前使用 SQLite backup API 保存一致快照，复制上传文件和私有配置；将快照下载到本机并校验 SHA-256、所有清单文件及 SQLite 完整性。需要恢复时只能恢复到新目录验证，不能覆盖在线目录。保护性全量备份可能包含短时注册请求等私有数据，应按备份访问权限保管，不公开。

## 社区数据

社区业务保存在 `content.db` 的 `community_` 表中：帖子、回复、编辑记录、赞、收藏、浏览、图片登记、举报；星尘流水、签到和补签；兑换所物品、兑换订单、已拥有的装扮和资源、道具卡；提示词解锁、资源“仍可用 / 已失效”投票；成员（信任等级、协管、装扮、公约同意时间）、访问天数、关注、通知、徽章和禁言记录。早期主站内嵌模式随主站 `content.db` 备份；当前香港独立模式还必须备份 `community-host.db` 中的进入会话、防重放与重试队列。香港不保存主站账号表；主站另保存 `reader-workflow.db` 和 `community-identity.db`，不能只备份一份 content.db 就宣称两站恢复完整。帖子和回复删除为软删除：记录保留，只是不再显示；编辑前的内容保留在编辑记录里供审核。

社区图片在上传时重新编码为 WebP，放在数据目录的 `uploads/` 下（`community-image-<id>.webp` 和缩略图 `community-thumb-<id>.webp`）。主站内嵌模式由 `scripts/backup-payload.mjs` 按 `community_images` 表写入备份清单，当前香港由 `scripts/backup-community.mjs` 备份社区库和完整上传目录，包括从帖子里移除、只做了软删除的图片。上传后一天内没有发出去的图片，会在之后的社区请求里（最多每分钟一次）连同文件一起清掉；同一步也处理超过 7 天没人采纳的悬赏（退回一半）。

首页与各板块的独立横幅配置保存在 `community_banners`、`community_banner_entries`，自定义封面登记在同一 `community_images` 表并保存在上述上传目录。它们随数据库和上传备份一并保留，不属于源码或旧版本清理。已有商品或横幅引用的图片不会按未使用上传过期删除；备份时这些引用的原图或缩略图缺失会使备份失败，不能把不完整结果当成成功备份。隐藏或删除关联帖子会停止公开展示，不会因此物理删除可恢复的配置。更新横幅表和图片用途约束仍使用既有社区迁移工具，先备份再事务迁移；详见 [横幅维护](COMMUNITY-BANNERS.md)。

`community_requests` 保存兑换、发帖、回复和感谢的已完成请求标识、正文哈希与结果，和结算／内容写入同一事务，随数据库备份保留。不得把它当临时缓存删除，否则旧请求重试可能再次扣分；不保存正文或收货地址副本。`community_rate_events` 保存账号操作频次，同数据库连接和进程重启后继续生效；沿用既有限速窗口，超过一天的事件由限速模块自动清理，不清理星尘或处罚记录。更新这两张表也须执行社区迁移，不能仅替换前端文件。

`community_audit_events` 是管理操作的持久审计，与上架、审核、删帖、禁言、任命和订单处理在同一事务写入，随数据库备份保留；审计落库失败则业务一起回滚。`reader-admin-audit.jsonl` 继续保存管理文件日志，但社区部分改为已提交事件的镜像。文件追加失败保留待镜像行、记录事件 ID 与错误码，后续请求继续重试，不把已成功操作假报为失败。镜像追加后、标记前异常退出可能使文件有同一 `auditEventId` 的重复行，以数据库事件和 ID 核对；不得清空待镜像审计来消除错误提示。

星尘余额以 `community_ledger` 流水为准，只追加不修改；内容被删、精华被取消时另写一条冲正记录，余额最低到 0。信任等级每个北京日在成员当天第一次访问时重算一次。

读者的头像只有审核通过的才会给其他已登录成员看（`/api/community/avatar/<UID>.webp`）。待审头像与个人主页背景只给本人及持有对应资料查阅权限的现任管理人员；审核建议与最终审批分别授权，不能凭职务名称访问或发布。头像、个签、昵称复用主站审核，个人主页背景在香港保存。已通过、待审背景图片都受备份和引用保护，不按一天未使用上传删除。权限、迁移与数据边界见 [社区资料维护](COMMUNITY-PROFILES.md) 和 [分级管理维护](COMMUNITY-STAFF.md)。

兑换实物时填写的收件人、手机号和地址只给站长在“社区管理 · 兑换发货”里看；订单标记发货或取消（取消会退回星尘和库存）时，这三项立即从 `community_orders` 删除。快递公司和单号分别保留在 `shipping_company`、`tracking_number`，用于发货通知和“我的兑换”记录。数字资源兑换后给出的内容（比如下载链接和提取码）由站长在“兑换所上架”里填写，只对已兑换的成员显示。

正式道具卡由作者保存为真实 `card` 商品，复用订单、库存和星尘结算，不将卡伪装成数字资源。误上架且尚无订单或拥有权益的物品可以纠正用途；已有历史兑换的物品保留用途，只能下架或另建正确商品。道具 schema 迁移、精确上下架更新、权益保护及旧版回滚限制见 [道具卡维护](COMMUNITY-SHOP-CARDS.md)。

可选的屏蔽词放在私有数据目录的 `community-words.txt`，每行一个词或短语，`#` 开头的行是注释；服务启动时读取，修改后需要重启。站长和协管的管理操作（删帖删回复、禁言与解除、置顶、精华、锁帖、移动、审核、恢复、改标签、举报处理、任命协管、发货、上架）都追加写入数据目录的 `reader-admin-audit.jsonl`，与读者管理共用这份私有审计日志，不公开、不提交。审核不通过时，固定理由和补充说明同时写入作者通知（附站务反馈入口）与审计记录。

站长管理身份不参与签到；签到、补签接口对管理身份返回 403，管理身份不出现在签到榜和贡献榜。切换后的专属个人读者身份按真实读者记录签到、发帖和互动，和管理身份账本分离；个人资料与博客品牌资料分离，配置、保护及首次准备见 [社区资料维护](COMMUNITY-PROFILES.md)。

首次上线社区前，以及社区更新带来新的表或字段时（包括订单的 `shipping_company`、`tracking_number`），先完成一次完整备份，再运行 `node scripts/migrate-community.mjs <private-payload-directory>`。脚本会先在数据目录的 `schema-backups/` 写入 `content.db` 快照，再在一个事务里补齐缺少的表和字段；已经建过早期社区表的数据库会就地升级，已有帖子和订单保留；什么都不缺时不做任何改动。未迁移时网站照常运行，社区接口只返回“社区尚未开放”。

2026-10-06 用户确认：非 VIP 读者连续六个自然月未登录后自动清理，有帖子、回复、星尘或兑换权益也不豁免。以最后一次成功登录计算；从未登录的账号以注册时间计算，按北京时间保留时分，月末按目标月最后一天计算。有效 VIP 仍保留，到期后按相同闲置条件判断。未验证注册请求的五分钟期限不变。

普通删帖／审核仍使用软删除；半年闲置账号清理是另一种永久删除：移除其全部主题（含此前软删除正文）、这些主题下的回复，以及该账号在其他主题的回复和关联编辑历史；清理其星尘、签到、关注、装扮、道具、兑换订单及相关互动数据。其他账号已获得的合法星尘不冲正；待发货订单返还库存，已发货订单不返还。清除失效横幅引用并更新版本；仍被其他有效横幅或商品引用的共享图片保留。UID 保留不可重用，登录安全记录和管理审计继续保留，不复制被清理的正文或收货资料。这取代 2026-10-02 的“有有效内容跳过 30 天清理”政策。

删除前在现有 `reader-workflow.db` 中记录持久清理任务；只有 `readers` 中账号已不存在时才能清理社区数据，社区删除在一个 SQLite 事务内完成。数据库清理失败、重启、图片删除失败均保留任务供后台重试；图片先登记到现有文件清理队列，仍有图片注册行时禁止删除文件。维护备份仍受既定保留周期管理，此功能不立即抹除历史备份。代码验证不等于执行生产清理；真实清理仍按本文的备份与候选核对流程执行。

## 保留规则

Payload 3.90.2 认证升级后的常规回滚必须保留新版认证依赖与当前数据，不能直接切回 3.89 或覆盖上线后的合法写入。升级与兼容回滚验证见 [认证安全升级](PAYLOAD-AUTH-UPGRADE.md)。

| 类别 | 规则 |
| --- | --- |
| 代码版本 | 保留当前版本与上一已验收版本；检查进程、systemd/Nginx 配置和保留版本符号链接后才清理其他版本 |
| 验证数据库与部署暂存 | 验收后先归档维护回执，再核对明确候选清单清理；不进行每日盲删 |
| 正式备份 | 至少保留最新三份完整备份，并保留最近十四天全部有效备份；任何保留副本校验失败时停止轮换 |
| 未知备份 | 清单损坏、没有创建时间、无法识别的目录一律保留，交由人工核对 |
| 发布准备副本 | 新机制仅清理有完成标记、超过七天且不属于最新三份或当前结果的副本；旧的无标记副本须核对后处理 |
| 静态资源版本 | 本次保留；今后至少保留三十天，始终保护当前与回滚版本引用，还要考虑长期开启的旧页面 |
| 日志 | 本次不清空登录或审计记录；容量管理应区分系统运行日志与业务审计记录 |

## 运维执行

`deploy/maintenance.py` 默认仅输出计划，不删除。生产脚本安装于 `/opt/sansphase-maintenance/maintenance.py`，与应用版本目录分离。默认 `--profile main` 使用主站固定目录；`--profile community` 只允许社区正式备份类别，不能清理其他目录。回执保存到 root 私有 `/var/log/sansphase-maintenance/`。未知目录、清单外文件、缺少日期或旧的损坏备份保留；已知近期或最新三份备份校验失败则整批停止，不退化为更旧的三份。

人工收尾：使用 `--categories releases,publication,stages,checks --plan /var/log/sansphase-maintenance/PLAN.json` 生成计划；确认当前及回滚版本、备份、进程引用及清单后，再加 `--apply`。两次计划不一致会拒绝执行。脚本不清理实时数据，也不清理静态资源或业务日志。

自动轮换：`sansphase-maintenance.timer` 每日调用 `--rotate-backups`，只清理已验证保留副本以外的过期备份；不会自动删除发布版本、验证数据库、用户、文章或头像。服务使用 systemd 写入目录限制，不能写入生产数据目录。保留每日备份的原有服务和时间安排。

社区轮换使用独立 `sansphase-community-maintenance.timer`，北京时间每天 06:30、最多随机延迟十五分钟，安排在每日社区备份后，降低 CPU 和磁盘优先级。它复用现有 `scripts/backup-community.mjs --verify` 核对两份库、上传引用和清单，不重写社区备份逻辑。

SQLite 的只读 WAL 校验仍可能在可写的备份目录生成辅助文件，见 [SQLite 官方只读 WAL 说明](https://www.sqlite.org/wal.html#read_only_databases)。两站已复验的已知产物仅限：清单登记的 `.db` 同路径同时存在零字节 `-wal` 和 32,768 字节 `-shm`，后者 SHA-256 为 `fd4c9fda9cd3f9ae7c962b0ddf37232294d55580e1aa165aa06129b8549389eb`，且二者均为无符号链接、无硬链接的普通文件，备份没有进程或配置引用。维护工具只将这对精确匹配的空校验产物识别为已知文件，验证时原样保留。非空 WAL、其他 SHM、单独的辅助文件、未登记数据库的辅助文件和其他未知文件继续拒绝；近期保留副本异常则停止整批轮换，旧异常副本保留。

社区官方校验在 Python 标准库建立的私有完整临时副本中执行，不再直接运行于正式备份；复制前后及校验结束时核对源目录身份和文件状态，源快照变化则停止。临时副本逐份创建并在本次验证结束后清理，因此校验期间需要足够容纳最大单份社区备份的临时磁盘空间；它不修改在线数据库、账号或上传目录。

社区删除另要求 `/var/log/sansphase-maintenance/community-offsite.json` 为 root 所有且权限 600。该回执使用 `sansphase-verified-offsite-v1` schema，`profile: community`、带时区的实际 `verifiedAt`，以及恰好三项 `backups`：每项保存已复验的真实目录名、`manifestSha256` 和异地 `archiveSha256`。只能在本机实际完成异地校验后安装，不能用伪造的 verified 标志代替验证。三份恢复锚点永久额外保留，后续新备份仍另按最新三份及十四天规则管理；更换锚点前重新完成异地校验。这是已完成异地验证的证明，不代表已经建设持续自动异地备份。

```sh
# 社区只生成计划；核对后以相同参数追加 --apply。
sudo python3 /opt/sansphase-maintenance/maintenance.py \
  --profile community \
  --offsite-receipt /var/log/sansphase-maintenance/community-offsite.json \
  --plan /var/log/sansphase-maintenance/community-backup-rotation.json
```

删除使用 Python 标准库的 FD 安全 rmtree，逐项核对父目录与候选身份；平台缺少保护时拒绝执行。第一项删除前写入进行中回执，每项成功后原子更新，失败停止并保留已完成清单。维护工具按提交版本单独安装与验收，不需要切换网站版本或修改在线数据库。

## 验证与后续发布

运行 `pnpm build`、`pnpm test`、`python -m unittest discover -s tests -p maintenance_test.py` 和 `pnpm release:prepare`。备份轮换和路径保护测试也在 CI 执行。涉及页面表现的改动仍需视觉验证，本次没有修改页面源码的业务表现。

新发布必须由准备清单创建空目录，Linux 依赖由锁文件安装；禁止 `cp -a old-release new-release`。每次收尾记录健康版本、数据差异原因、文件完整性及可用磁盘。无关的样式重构和死代码删除另立改动，不与容量清理混合。
